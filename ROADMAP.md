## Found While Implementing

Added 2026-09-06 while draining the research-driven batch. IDs continue the RD scheme; RD-212 was the last used.

- [ ] P2: RD-214: Stop crediting a repository that does not exist, and keep the shipped notices in step
  Why: the first row of the App's third-party notices links `https://github.com/SysAdminDoc/LibreSpot-Prism` at commit `72dc0334fdf11a156314c96593539e477aee7028`. That repository was never pushed; `gh repo view SysAdminDoc/LibreSpot-Prism` answers "Could not resolve to a Repository". The commit existed only in a local folder and now survives as the `refs/archive/prism-origin` ref in this repository. Prism is first-party work in any case, so a third-party attribution table is the wrong home for it, and a licence notice that cites a dead URL is the one file that should never be wrong.
  Evidence: `src/LibreSpot.App/THIRD_PARTY_NOTICES.md:9`; `git log refs/archive/prism-origin` shows the two original commits; `resources/themes/Prism/` holds the shipped theme; every other row in the table resolves.
  Touches: `src/LibreSpot.App/THIRD_PARTY_NOTICES.md`, `resources/custom-apps/librespot-engine.zip`, `src/powershell/data/CommunityCustomApps.ps1`, `src/LibreSpot.Desktop/Backend/LibreSpot.Backend.ps1`, `LibreSpot.ps1`, `tests/LibreSpot.Desktop.Tests/`.
  Note: not a one-line edit. The notices file ships inside `librespot-engine.zip`, whose SHA256 is pinned in three places, so the text change means repackaging and re-pinning. `BundledLibreSpotArchive_MatchesEveryPinAndShipsItsPackageVersion` checks the archive against all three pins and will catch a half-done change.
  Acceptance: the notices SHALL carry no link to a repository that does not resolve, Prism SHALL be described as first-party with its origin commit and the ref that preserves it, the rebuilt archive SHALL match its three pins, and a test SHALL fail when a row in the table names a repository the file does not also record as first-party.
  Complexity: M

- [ ] P2: RD-215: Resolve the orphaned Prism vendor copy against the theme that actually ships
  Why: nothing in the repository references `src/LibreSpot.App/vendor/librespot-prism/`; a grep for `librespot-prism` outside that directory returns nothing. Its `theme.js` is ahead of the copy that ships: commit `a262159` wrapped the settings-menu registration in a retry that backs off up to twenty times and added guards for `Spicetify.React`, `ReactDOM` and `PopupModal`, and none of that reached `resources/themes/Prism/theme.js`, which still calls `new Spicetify.Menu.Item(...).register()` bare. Either the shipped theme has the race that retry was written to survive, or the fix is dead code. Its `color.ini` has drifted too (`button-disabled =3F3F3F` with the spacing lost, and an extra space on `player`).
  Evidence: `git log --oneline -- src/LibreSpot.App/vendor/librespot-prism/theme.js` gives `a262159` and `ab68ab8`, against a single `57b65b9` for `resources/themes/Prism/theme.js`; the shipped copy is 7,663 bytes and the vendor copy 8,069; `resources/themes/Prism/theme.js` hashes to `1e2e2c84...`, pinned in `LibreSpot.ps1:1594`, `src/LibreSpot.Desktop/Backend/LibreSpot.Backend.ps1:265` and `src/powershell/data/BundledThemes.ps1:16`, while the vendor copy's `ce3f6881...` is pinned nowhere.
  Touches: `resources/themes/Prism/`, `src/LibreSpot.App/vendor/librespot-prism/`, `LibreSpot.ps1`, `src/LibreSpot.Desktop/Backend/LibreSpot.Backend.ps1`, `src/powershell/data/BundledThemes.ps1`, `tests/`.
  Acceptance: exactly one Prism source SHALL remain in the tree; if the retry is a real fix it SHALL be forward-ported into the shipped theme with all three pinned hashes updated together, and if it is not the vendor directory SHALL be deleted; either way a test SHALL fail when a second copy of a bundled theme's `theme.js` appears with a hash no pin records.
  Complexity: M

- [ ] P3: RD-213: Check for ps2exe in the host that will actually import it
  Why: `Invoke-LibreSpotStableExeCompile` decides whether ps2exe is available with `Get-Module -ListAvailable` in whichever host is running `Build-Scripts.ps1`, then compiles by shelling out to `pwsh`. Those are different module scopes. The documented way to run the build is under Windows PowerShell, so a developer who installs ps2exe from PowerShell 7 (the reasonable reading, since the comment right above says ps2exe targets PowerShell 7 on this toolchain) lands it in `Documents\PowerShell\Modules`, and the check rejects a setup the compile step would have handled: the child `pwsh` inherits `PSModulePath` from its Windows PowerShell parent and can see the Windows PowerShell user scope the parent checked. The thrown message then repeats the same `Install-Module -Scope CurrentUser` that put it in the wrong place.
  Evidence: reproduced 2026-09-06. With ps2exe 1.0.18 present only in `Documents\PowerShell\Modules`, `Build-Scripts.ps1 -CompileStableExe` under Windows PowerShell throws "ps2exe 1.0.18 is required" at `Build-Scripts.ps1:1977`; installing the same version into the Windows PowerShell scope makes the identical command compile and pass `Test-LibreSpotStableExeIdentity`. With the PowerShell 7 copy renamed away, the compile still succeeds, because the inherited `PSModulePath` carries the Windows PowerShell user directory into the child.
  Touches: `Build-Scripts.ps1`, `CLAUDE.md`.
  Acceptance: the availability check SHALL ask the same host that runs the compile, so a version reachable by that host is accepted and one that is not is refused; WHEN the module is missing the message SHALL name the host and the module directory it searched rather than a bare `Install-Module` line; and a compile that the check accepted SHALL NOT fail on the import.
  Complexity: S
